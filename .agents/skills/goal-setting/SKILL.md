# 目的設定スキル (Goal-Setting Protocol)

このスキルは、人間が「〜したい」「〜を作りたい」「〜を考えて」と発話した際、または要件定義・機能追加の初期フェーズ（PHASE_1a）で自動的にロードされる。

---

## 1. 鉄の原則（ブレーキ）
- **コードは1行も書かない。**
- **設計書もまだ更新しない。**
- **対話の流れを止めず、目的の解像度を上げることに集中する。**

---

## 2. 目的確定のためのヒアリングと照合項目
人間の要望を受けたら、以下の手順で目的を明確にする：

0. **Project Scope Check（プロジェクト目的との照合）**:
   - `docs/concept.md` が存在する場合、その内容（Why / In-Scope / Out-of-Scope）を確認する。
   - 要望がプロジェクトの主目的に合致しているか確認し、もし Out-of-Scope に該当しそうな場合は「`concept.md` の想定スコープ外に見えますが、目的を拡張しますか？」と確認を挟む。
1. **Why（機能の目的・動機）**:
   - なぜこれを作るのか？解決したい本質的な課題やペインは何か？
2. **Who（対象ユーザー・文脈）**:
   - 誰が、どのような状況で使うのか？
3. **Non-Goal（あえてやらないこと）**:
   - スコープクリープ（機能の肥大化）を防ぐため、今回は「意図してやらないこと」は何か？
4. **DoD（完了の定義 / Definition of Done）**:
   - 何をもって「完成・成功」と判定するか？（具体的な受け入れ条件や動作テスト結果）

---

## 3. 合意形成と要約プロトコル
質問をぶつけるだけでなく、対話の節目で必ず以下のフォーマットで要約を提示し、人間の合意（「それでいこう」「OK」等）を得ること：

```text
【目的設定の要約】
- プロジェクト整合: docs/concept.md 照合済み（In-Scope）
- 機能目的 (Why): ...
- 対象 (Who): ...
- やらないこと (Non-Goal): ...
- 完了条件 (DoD): ...

この方針で合意いただければ、仕様の固定と実装段取りに進みます。よろしいですか？
```

合意が得られたら、本スキルを終了し、自律的に書類更新（PHASE_1b）へ移行する。
