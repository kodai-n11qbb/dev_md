# CODING_RULES.md

> 本ファイルは実装フェーズ（PHASE_3）における厳格なコード規約である。
> "The best code is the code you never wrote."（書かないコードが最善のコード）

---

## 1. Ponytail 7段階判断ラダー（過剰設計の撲滅）
コードを書く前に、必ず以下のラダーを上から順に検討し、最初に該当した最上位の手段を採用すること：

1. **YAGNI (You Aren't Gonna Need It)**: 不要な先回り実装は書かない。
2. **既存コード再利用**: リポジトリ内の共通処理・関数で済ませられないか確認する。
3. **標準機能・ライブラリ**: 言語組み込みの機能でシンプルに書けないか。
4. **プラットフォーム標準**: ブラウザ・OSの標準APIで解決できないか。
5. **導入済みパッケージ**: 新規npm/pipパッケージを追加せず、既存の依存関係で解けないか。
6. **1行解決**: クラスや複雑な関数を作らず、1〜数行で表現できないか。
7. **最小限の自作**: 上記で解決できない場合のみ、最小限のコードを書く。

## 2. 業界標準の品質・テスト保証（妥協の禁止）
- **Refactor-ready Test**: テストがないコードは負債とみなす。
- **テスト環境の自己構築**:
  - テスト環境が存在しないリポジトリの場合、**実装コードを書く前にまず最小限のテストランナー（Vitest, Jest, pytest等）を導入すること。**「テスト環境がないためテストを省略した」という言い訳は禁止する。
- **テスト必須要件**:
  - 正常系（Happy Path）だけでなく、**境界値（Boundary）**および**異常系・エラーハンドリング**のテストを必ず含めること。
- **型安全性・静的解析**:
  - 型定義を省略しない。Linter / Formatter が設定されている場合は、エラーゼロを確認してから完了とすること。

---

## 3. アーキテクチャ原則
- **Dependency Injection (DI)**: 具象クラスを直接 new せず、外から渡せるようにしてテスト容易性を保つ。
- **Rule of Three**: 同じコードが3回出てくるまで、性急な共通化・抽象化をしない。
- **Performance Escape Hatch**: 性能上クリティカルな箇所（Hot Path）に限り、コメントで理由を明記して上記ルールを逸脱することを許可する。

---

## 4. 便利ツールの試用・導入（Spike）と撤退リミッター
- **事前確認**: 新規ツール検討時はまず `docs/decision-log.md` を確認し、検証済みのものは再検証しない。
- **撤退リミッター（トークン浪費防止）**: ツールの試用・設定で**2回連続失敗**した場合は深追いせず、即座に標準実装へ切り替える。
- **ADR記録**: 採否に関わらず、理由を1行 `docs/decision-log.md` に記録する。
